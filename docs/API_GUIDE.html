Chapter 1

전체 워크플로우 개요

사용자는 4단계 순서를 따른다. 각 단계는 이전 단계의 결과에 의존한다.

stateDiagram-v2 [*] --> Step1 : Login Step1 --> Step2 : Accounts selected Step2 --> Step3 : Keywords confirmed Step3 --> Step4 : Template chosen Step4 --> Monitor : Run started Monitor --> [*] : All done state Step1 { direction LR upload_acct : Upload Excel preview_acct : Review rows confirm_acct : Save and select upload_acct --> preview_acct preview_acct --> confirm_acct } state Step2 { direction LR upload_kw : Upload Excel preview_kw : Review categories confirm_kw : Save and select upload_kw --> preview_kw preview_kw --> confirm_kw } state Step3 { direction LR list_tmpl : List templates preview_tmpl : Preview post list_tmpl --> preview_tmpl } state Step4 { direction LR preview_run : Preview plan execute_run : Execute preview_run --> execute_run } state Monitor { direction LR list_runs : List runs detail_run : View detail retry_or_stop : Retry or Stop list_runs --> detail_run detail_run --> retry_or_stop }

그림 1-1. 전체 워크플로우 상태 다이어그램

모든 단계에서 공통 패턴은 동일하다: 업로드(파싱만) → 미리보기 → 확인(저장). 프론트엔드는 확인(confirm) 버튼을 누르기 전까지 서버에 아무것도 저장하지 않는다는 점을 사용자에게 알려주어야 한다.

Chapter 2

인증

모든 API 호출에는 JWT Bearer 토큰이 필요하다. 로그인 후 받은 토큰을 Authorization: Bearer <token> 헤더에 포함한다.

POST /auth/login

// Request
{
    "email": "user@example.com",
    "password": "secret"
}

// Response 200
{
    "token": "eyJhbGciOiJIUzI1NiIs...",
    "user": {
        "display_name": "Eric",
        "email": "user@example.com"
    }
}

// Response 401
{
    "success": false,
    "message": "Email or password is incorrect.",
    "suggestion": "Check your email spelling."
}

Chapter 3

Step 1 — 계정 엑셀 업로드 & 선택

사용자는 블로그 플랫폼 계정이 담긴 엑셀 파일을 업로드한다. 시스템이 파싱 결과를 미리보기로 보여주고, 사용자가 확인하면 저장된다.

시퀀스 다이어그램

sequenceDiagram actor User participant FE as Frontend participant API as /api/spa/v1 User->>FE: Select accounts.xlsx FE->>API: POST /step1/accounts/upload (multipart) API-->>FE: AccountUploadPreview FE-->>User: Show table with valid/invalid rows User->>FE: Check rows, click "Confirm" FE->>API: POST /step1/accounts/confirm API-->>FE: AccountConfirmResult FE-->>User: "3 accounts saved. 2 selected."

그림 3-1. Step 1 계정 업로드 시퀀스

엔드포인트 상세

POST /step1/accounts/upload

엑셀 파일을 파싱만 한다. DB에 저장하지 않는다.

엑셀 필수 열: username, password, platform. 선택 열: blog_id, cooldown_days.

// Request: multipart/form-data
// field "file": accounts.xlsx

// Response 200 — AccountUploadPreview
{
    "success": true,
    "rows": [
        {
            "row_number": 1,
            "username": "myblog01",
            "platform": "naver",
            "blog_id": "myblog",
            "valid": true,
            "error": null
        },
        {
            "row_number": 2,
            "username": "",
            "platform": "naver",
            "blog_id": "",
            "valid": false,
            "error": "Missing password"
        }
    ],
    "valid_count": 1,
    "invalid_count": 1
}

프론트엔드는 valid: false인 행을 빨간색으로 표시하고, error 메시지를 해당 행 옆에 보여준다. 유효하지 않은 행은 confirm에서 제외해야 한다.

POST /step1/accounts/confirm

미리보기에서 확인된 계정을 DB에 저장하고, 이번 실행에 사용할 계정을 선택한다.

// Request — AccountConfirmInput
{
    "accounts": [
        {
            "username": "myblog01",
            "password": "pw1234",
            "platform": "naver",
            "blog_id": "myblog",
            "cooldown_days": 14
        }
    ],
    "selected": [0]
}

// Response 200 — AccountConfirmResult
{
    "success": true,
    "message": "1 account saved. 1 selected for posting.",
    "saved_count": 1,
    "selected_count": 1
}

selected 배열은 accounts 배열의 0-based 인덱스이다. 사용자가 체크박스로 선택한 행의 인덱스를 보낸다.

GET /step1/accounts

이미 저장된 계정 목록을 조회한다. 재업로드 없이 선택만 바꿀 때 사용한다.

// Response 200 — AccountView[]
[
    {
        "id": 1,
        "username": "myblog01",
        "platform": "naver",
        "status": "Ready",
        "selected": true,
        "last_used": "15 days ago"
    },
    {
        "id": 2,
        "username": "myblog02",
        "platform": "naver",
        "status": "Cooling (3 days left)",
        "selected": false,
        "last_used": "11 days ago"
    }
]

status 필드는 사람이 읽을 수 있는 문자열이다. 프론트엔드는 이 값을 그대로 표시하면 된다. "Cooling" 상태인 계정은 선택 불가로 표시한다.

PUT /step1/accounts/select

기존 계정 중 이번 실행에 사용할 계정을 변경한다.

// Request
{
    "account_ids": [1, 3]
}

// Response 200 — AccountConfirmResult
{
    "success": true,
    "message": "2 accounts selected for posting.",
    "saved_count": 0,
    "selected_count": 2
}

Chapter 4

Step 2 — 키워드 엑셀 업로드 & 선택

사용자는 키워드가 담긴 엑셀 파일을 업로드한다. 각 열이 하나의 키워드 카테고리(예: 지역, 과목)가 되고, 각 행의 값이 개별 키워드가 된다.

시퀀스 다이어그램

sequenceDiagram actor User participant FE as Frontend participant API as /api/spa/v1 User->>FE: Select keywords.xlsx FE->>API: POST /step2/keywords/upload (multipart) API-->>FE: KeywordUploadPreview FE-->>User: Show categories, keyword counts, samples User->>FE: Enter campaign name, click "Confirm" FE->>API: POST /step2/keywords/confirm API-->>FE: KeywordConfirmResult FE-->>User: "2 categories, 45 keywords. Title: {region} {subject}" opt Upload pool Excel User->>FE: Select pools.xlsx FE->>API: POST /step2/pools/upload (multipart) API-->>FE: PoolUploadResult FE-->>User: "2 pools imported: salt_prefix(5), salt_suffix(8)" end

그림 4-1. Step 2 키워드 업로드 시퀀스

엔드포인트 상세

POST /step2/keywords/upload

키워드 엑셀을 파싱만 한다. DB에 저장하지 않는다.

// Request: multipart/form-data
// field "file": keywords.xlsx

// Response 200 — KeywordUploadPreview
{
    "success": true,
    "categories": [
        {
            "column_name": "지역",
            "slug": "region",
            "keyword_count": 25,
            "sample_values": ["강남", "수원", "분당", "일산", "판교"],
            "detected_affixes": ["suffix: 동, 구, 시"]
        },
        {
            "column_name": "과목",
            "slug": "subject",
            "keyword_count": 8,
            "sample_values": ["수학", "영어", "국어", "과학", "사회"],
            "detected_affixes": []
        }
    ],
    "total_keywords": 33,
    "estimated_combinations": 200
}

estimated_combinations는 카테고리별 키워드 수의 곱(카르테시안 곱)이다. 사용자에게 "약 200개의 포스트가 생성됩니다"라고 안내한다.

POST /step2/keywords/confirm

키워드를 DB에 저장하고 캠페인을 생성한다. 제목 템플릿은 엑셀 열 순서(왼쪽→오른쪽)대로 자동 생성된다.

// Request — KeywordConfirmInput
{
    "campaign_name": "강남 과외 캠페인",
    "platform_id": 1,
    "categories": [
        {
            "slug": "region",
            "values": ["강남", "수원", "분당"]
        },
        {
            "slug": "subject",
            "values": ["수학", "영어"]
        }
    ]
}

// Response 200 — KeywordConfirmResult
{
    "success": true,
    "message": "2 categories, 5 keywords saved. Title: {region} {subject}",
    "campaign_id": 42,
    "title_template": "{region} {subject}",
    "combination_count": 6
}

categories[].values는 사용자가 미리보기에서 선택한 키워드만 포함한다. 전체 키워드 중 일부를 체크 해제하면 이 배열에서 빠진다.

응답의 campaign_id는 이후 Step 3, Step 4에서 필요하다. 프론트엔드가 상태로 보관해야 한다.

GET /step2/keywords

저장된 키워드를 카테고리별로 조회한다. 재선택 시 사용한다.

// GET /step2/keywords?campaign_id=42
// Response 200 — KeywordCategoryView[]
[
    {
        "slug": "region",
        "name": "지역",
        "keywords": [
            { "id": 1, "value": "강남", "selected": true },
            { "id": 2, "value": "수원", "selected": true },
            { "id": 3, "value": "분당", "selected": false }
        ]
    }
]

PUT /step2/keywords/select

기존 키워드의 선택 상태를 변경한다.

// Request — KeywordSelectInput
{
    "campaign_id": 42,
    "categories": [
        { "slug": "region", "keyword_ids": [1, 2] },
        { "slug": "subject", "keyword_ids": [5, 6] }
    ]
}

POST /step2/pools/upload (선택)

제목 장식용 풀(salt_prefix, salt_suffix 등)을 업로드한다. 제목에 랜덤 변형을 추가할 때 사용한다.

// Request: multipart/form-data
// field "file": pools.xlsx

// Response 200 — PoolUploadResult
{
    "success": true,
    "message": "2 pools imported.",
    "pools": [
        {
            "slug": "salt_prefix",
            "count": 5,
            "samples": ["검증된", "전문", "인기"]
        },
        {
            "slug": "salt_suffix",
            "count": 8,
            "samples": ["강력 추천", "즉시 가능", "무료 상담"]
        }
    ]
}

미리 정해진 포스트 레이아웃 템플릿 중 하나를 선택한다. 템플릿은 블록의 순서를 정의한다(제목 → 단락 → 이미지 → 단락 → ...).

Chapter 6

Step 4 — 실행 옵션 & 실행

캠페인, 템플릿, 계정이 모두 준비되면 발행 모드를 선택하고 실행한다.

시퀀스 다이어그램

sequenceDiagram actor User participant FE as Frontend participant API as /api/spa/v1 User->>FE: Choose "immediate" or "scheduled" FE->>API: POST /step4/run/preview API-->>FE: RunPreviewView FE-->>User: "180 posts, 3 accounts, ~2 hours" User->>FE: Click "Go" FE->>API: POST /step4/run/execute API-->>FE: RunStartResult FE-->>User: "180 posts scheduled. First at 2:00 PM." FE->>FE: Navigate to Monitor

그림 6-1. Step 4 실행 시퀀스

엔드포인트 상세

POST /step4/run/preview

실행 계획을 미리보기한다. 아직 실행하지 않는다.

// Request — RunConfig
{
    "campaign_id": 42,
    "template_id": 5,
    "publish_mode": "scheduled",
    "schedule_start": "2026-03-23T14:00:00+09:00",
    "schedule_interval_minutes": 60,
    "headless": true
}

// Response 200 — RunPreviewView
{
    "campaign_name": "강남 과외 캠페인",
    "template_name": "Standard SEO Post",
    "total_combinations": 180,
    "accounts": [
        { "username": "myblog01", "posts_assigned": 40 },
        { "username": "myblog02", "posts_assigned": 40 },
        { "username": "myblog03", "posts_assigned": 40 }
    ],
    "publish_mode": "scheduled",
    "schedule_summary": "Starting 3/23 2:00 PM, one post every 60 min",
    "estimated_finish": "3/24 8:00 AM",
    "sample_titles": [
        "강남 수학 과외 전문 추천",
        "수원 영어 과외 검증된 강력 추천",
        "분당 수학 과외 즉시 가능"
    ],
    "warnings": []
}

warnings 배열이 비어있지 않으면 사용자에게 경고를 표시한다. 예: "Pool salt_prefix has no values — title slots will be empty."

POST /step4/run/execute

실행을 시작한다. 요청 본문은 preview와 동일한 RunConfig이다.

// Request — RunConfig (same as preview)

// Response 201 — RunStartResult
{
    "success": true,
    "message": "180 posts scheduled across 3 accounts.",
    "batch_ids": [101, 102, 103],
    "total_posts": 180
}

batch_ids는 모니터링에 사용된다. 프론트엔드는 이 값을 저장하고 모니터 화면으로 이동한다.

RunConfig 필드 규칙

필드필수규칙
campaign_idYStep 2에서 받은 값
template_idYStep 3에서 선택한 값
publish_modeY"immediate" 또는 "scheduled"
schedule_start조건부scheduled일 때 필수. ISO 8601 + timezone.
schedule_interval_minutesN기본 60. scheduled일 때만 의미.
headlessN기본 true. 디버그 시 false.

Chapter 7

모니터링

실행이 시작된 후 진행 상황을 확인하고, 실패한 항목을 재시도하거나 실행을 중지할 수 있다.

배치 상태 다이어그램

stateDiagram-v2 [*] --> pending : dispatch pending --> running : worker picks up running --> completed : all items done running --> failed : all items failed running --> stopped : cancel requested stopped --> pending : retry failed --> pending : retry pending --> running : worker picks up

그림 7-1. 배치 상태 전이 — stopped과 retry 추가

개별 항목 상태 다이어그램

stateDiagram-v2 [*] --> pending pending --> running : processing running --> completed : success running --> failed : error pending --> cancelled : batch stopped failed --> pending : retry cancelled --> pending : retry

그림 7-2. 배치 항목(BatchItem) 상태 전이

모니터링 시퀀스 다이어그램

sequenceDiagram actor User participant FE as Frontend participant API as /api/spa/v1 FE->>API: GET /monitor/runs API-->>FE: RunProgressView[] FE-->>User: Show batch list with progress bars User->>FE: Click a batch FE->>API: GET /monitor/runs/101 API-->>FE: RunDetailView FE-->>User: Show item-level details alt Some items failed User->>FE: Click "Retry Failed" FE->>API: POST /monitor/runs/101/retry API-->>FE: { success: true, message: "3 items will be retried." } end alt Want to stop User->>FE: Click "Stop" FE->>API: POST /monitor/runs/101/stop API-->>FE: { success: true, message: "Batch stopped. 25 items cancelled." } end

}

POST /monitor/runs/{batchId}/retry

실패한 항목과 취소된 항목을 재시도 대기 상태로 되돌린다.

// Response 200
{
    "success": true,
    "message": "3 items will be retried."
}

재시도 후 배치 상태가 pending으로 돌아간다. 워커가 다시 해당 배치를 처리한다.

POST /monitor/runs/{batchId}/stop

실행 중인 배치를 중지한다. 현재 처리 중인 항목은 완료되고, 아직 시작하지 않은 항목은 cancelled로 표시된다.

// Response 200
{
    "success": true,
    "message": "Batch stopped. 25 items cancelled."
}

중지 후에도 retry를 호출하면 취소된 항목을 재시도할 수 있다.

Chapter 8

에러 처리 규칙

모든 에러 응답은 동일한 FriendlyError 형태를 따른다.

// FriendlyError schema
{
    "success": false,
    "message": "What went wrong, in the user's language.",
    "suggestion": "What the user can do about it."
}

HTTP 상태 코드 규칙

코드의미프론트엔드 동작
200성공정상 처리
201생성 성공다음 단계로 이동
401인증 실패로그인 화면으로 이동
422입력 검증 실패message와 suggestion 표시
500서버 오류"일시적인 오류" 메시지 + 재시도 버튼

프론트엔드 에러 표시 규칙

첫째, message는 반드시 사용자에게 표시한다. 기술 용어가 포함되지 않은 사람의 언어이다.

둘째, suggestion이 있으면 message 아래에 작은 글씨로 표시한다. 사용자가 다음에 취할 행동을 안내한다.

셋째, HTTP 상태 코드나 내부 에러 코드는 절대 사용자에게 보여주지 않는다.
